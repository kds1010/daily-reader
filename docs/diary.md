# 記録から作る日記

iPhone・macOSの「今日」→「日記」から、日付ごとの下書きと根拠を確認し、文章を編集して保存できます。日本時間（Asia/Tokyo）で日付を選びます。下書きはMac mini内のテンプレートで作成し、外部AI、検索、APIキー、追加の権限を使いません。

## 材料と表現

- 通常タスクの完了日時、日付ごとのルーティン完了、暮らしのタスク・予定の完了記録を読みます。未完了タスクの期限を実績として扱いません。
- 健康の日次集計、本人が入力した疲労度・気分・体調メモをそのまま載せます。未取得を0にせず、健康評価や気持ちを推測しません。ルーティンと健康の既存日付キーは端末で確定したものとして扱い、旅行中もタイムスタンプだけで別日へ移動しません。
- 解析済みで録音日時が確認済みの会話の話題と記録を載せます。取込日時を録音日時に代用しません。話題の説明は発言の抜粋で、本人の発言・感情・行動とは断定しません。録音を開始した日本時間の日付へまとめ、発言を日跨ぎで再分配しません。
- 暮らしと同期済みカレンダーの予定は「参加実績は未確認」と明示します。日跨ぎ予定は対象日との重なりを確認し、暮らしの項目IDで連携済みの予定と端末間の同一予定を重複排除します。中止済みの暮らしの予定をカレンダーの残存コピーから再表示しません。
- カレンダーの未取得・停止・拒否・取得失敗・取得範囲不足・24時間を超える古い同期を区別します。一時的な取得失敗では前回の予定を警告付きで使います。
- GPS、メール本文、Agent履歴、人物プロフィールは材料に含めません。原音・文字起こし処理の既存の送信設定は別機能であり、日記生成からCodexを呼ぶことはありません。

材料がない日は、そのことを表示します。「何もしなかった日」とは表現しません。下書きは種類別に最大20件、全体20000文字までです。省略された内容は根拠一覧で確認できます。

## 自動更新・編集・削除

Webサーバー内の`DiaryWorker`が起動時と5分ごとに、当日と過去7日を確認します。導入日時以降が自動対象です。8日以上前や導入前の日記は日付を選び、手動で作成・更新できます。未来日は生成できません。サーバー停止中には生成されず、再起動時に対象期間を再確認します。

材料と生成方式が変わったときだけ自動下書きを更新します。同じ値の健康同期や会話の話題ID再採番だけでは改訂しません。取得失敗やDB障害時は保存済みの日記を保持して次の周期に再試行します。

自動本文と本人の本文は別々に保存します。本人の文章を自動更新で上書きしません。編集・削除・手動生成には改訂番号が必要で、別端末や自動処理による更新と競合した場合はHTTP 409を返します。画面では入力を保持し、最新の日記と比較した後、確認した改訂に対して保存できます。未保存の入力はアプリの稼働中、日付を切り替えても保持します。アプリ終了後の復元やオフライン保存は初期版に含めません。

自動生成を停止すると新しい自動更新を止めます。保存済みの日記の閲覧・編集と手動生成は利用できます。再開後の自動更新は同じ期間制限に従います。

日記を削除すると本文、根拠のコピー、改訂履歴を削除し、削除済みの印を残して自動再作成を防ぎます。元のタスク、健康、会話、予定は変更しません。画面から明示的に再作成できます。端末バックアップやDBファイルの安全消去を保証する機能ではありません。

## 保存と実装

`data/planner.sqlite3`の`diary_entries`、`diary_settings`、`diary_revisions`に保存します。安全な生成失敗メッセージだけを`diary_generation_errors`へ保存し、画面に表示します。日記本体と本人の保存時点の根拠は削除するまで保持し、旧版は日付ごとに直近20版まで保持します。元記録が後から訂正・削除されても、保存時点の根拠を確認できます。日記を削除する際はこれらのコピーも削除します。Git管理・静的サイト・SideStore配信の対象にはしません。

- `src/daily_reader/diary.py`: 入力収集、テンプレート生成、競合検出、保存、ワーカー。
- `daily_planner.diary_records`: 「今日」一覧で除外される通常タスクの完了と、日付別ルーティン・健康の読取。
- `life_revisions`: 変更前の状態と変更時刻を順に比較し、完了への遷移を復元します。通常の編集時刻を完了日時に代用しません。
- `local_server.py`: `GET /api/diary?date=YYYY-MM-DD`と`GET /api/diary/settings`。GETは生成を起動しません。`POST /api/diary/generate`はdate/revision（新規は0）、`save`はdate/revision/body、`delete`はdate/revision、`settings`はenabledを受け取ります。本文上限20000文字、POST上限160000 bytes、JSON必須、別オリジンの書込は拒否します。
- `ios/DailyReader/DailyReader/Diary.swift`: 両OS共通のモデル、編集状態、画面。日記の取得失敗が他の画面を利用不可にしません。

## 検証と配信

`tests/test_diary.py`で日付境界、入力条件、重複、履歴、編集保持、停止、再起動、同時更新、取得失敗、外部処理なしを検証します。`tests/test_local_server.py`でJSON/APIと競合を確認し、`tests/test_diary_native.py`で実際のAPI形式とSwiftの相互変換、日付別入力、競合、削除、fixtureのAPI非呼出しを実行します。

Debugの`-daymeld-fixture standard|empty|partial-failure|stress|in-flight`が日記にも対応します。in-flightでは初回保存時に別端末による更新を再現します。fixtureは個人データや実APIを使いません。

既存のruff、pytest、JavaScript・JSON・diff検証に加え、DailyReaderのiphoneos DebugとDaymeldMacのmacosx Debugを署名なしでビルドします。main統合・push後はWebサーバーのLaunchAgentを再起動し、APIと既存の3ポート・Tailscale境界を検証します。両OSの配布成果物を再生成・検証して配信します。Agentワーカーの再起動は不要です。iPhone実機へのインストールは独立した工程です。
