# iPhoneから自動取得する生活コンテキスト

2026-09-07実装。目的は、入力項目を増やさず、既存予定との重なり、着手できそうな時間、会話時の状況を確認できるようにすることです。取得したカレンダー・移動・健康データをCodexへ送りません。会話からの明示的な用事抽出と公開Web調査は従来の範囲で動きます。

## 取得と利用

| 情報 | 自動取得のタイミング | 利用先 |
| --- | --- | --- |
| 既存カレンダーの件名・開始終了・場所・空き扱い | full access許可後の前景更新、BGAppRefresh。成功後15分は再取得しない | 今日から先の予定、予定重複の確認、今日8〜21時のカレンダー上の20分着手枠を最大3件、会話と同時刻の予定 |
| Core Motionの静止・歩行・走行・自転車・自動車等の推定 | モーションとフィットネスの初回許可後、同じ更新時 | 録音開始と音声内の各発言時刻の参考情報 |
| GPSの速度・速度精度・シミュレーションフラグ | 既存の位置取得・移動記録の更新と同時。追加の権限不要 | 移動中の、古いGPSとの誤った場所紐付けを減らす |
| HealthKitの既存5種の日次集計 | 初回の認証操作を済ませた後、前景/BGAppRefreshの機会に最短30分間隔 | 「今日」の体調集計。疲労度や病気を自動推定しない |
| 端末のタイムゾーン | カレンダー・移動の同期と同時 | 今日の日付・作業枠の表示用地域時刻 |

カレンダーは直近7日〜今後14日のスナップショットを取得します。メモ本文、参加者、連絡先、カレンダーのアカウント識別情報は送信しません。端末IDはアプリが生成したUUID、予定IDはEventKit識別子と開始日時をハッシュ化したものです。既存の録音ファイル名を日本時間として読む規則は変更しません。

Core Motionは最大7日分の履歴を照会します。低確信度・複数状態の同時検出・不明状態を確定扱いせず、1区間の継続は30分までに制限します。問い合わせは8秒で打ち切れます。取得できない区間を周辺の状態で補間しません。システムの履歴には遅れがあり、過去の全区間が残る保証はありません。[Appleの履歴取得仕様](https://developer.apple.com/documentation/coremotion/cmmotionactivitymanager/queryactivitystarting(from:to:to:withhandler:))。

カレンダー上の空き時間は、実際に本人が暇であることやタスクが20分で終わることを意味しません。予定の入っていない20分を着手候補として提示し、カレンダーへの作業枠登録や自動完了は行いません。24時間以内の成功したカレンダー同期がその日をカバーする場合だけ提示します。期限がこれから来るタスクは、その期限内に収まる枠を選びます。

## 紐付けと精度

- 録音の確認済み開始日時、音声発言の開始秒から得た時刻を、半開区間`開始 <= 時刻 < 終了`でカレンダー・移動区間へ照合します。TXTの行番号を発言時刻には使いません。
- 「同時刻のカレンダー」は参加した証明ではありません。参加者、同席者、声の人物同定、第三者の関心・属性の推定に使いません。複数候補は複数のまま表示します。
- 現在の関連は新しい同期で変わります。暮らしの項目作成時に固定する会話根拠の位置コンテキストには、その時点の端末コンテキストも含みます。再解析前の既存スナップショットは上書きしません。
- GPS方式版は`nearest-gps-v2`です。従来の前後5分・水平精度200m・精密位置の条件に加え、シミュレーション位置を除外します。速度と速度精度が有効なら`水平精度 + (速度 + 速度精度) × 時刻差 <= 300m`を満たす候補だけを使います。300mはアプリの保守的な照合条件であり、移動距離や位置の保証ではありません。速度が不明な旧データは従来条件を使います。[Appleの速度精度の定義](https://developer.apple.com/documentation/corelocation/cllocation/speedaccuracy)。
- 新しい会話からの参加予定が既存カレンダーの用事と重なる場合は、日時入りの確認候補へ戻します。EventKitへの自動書き込み時にも重複・競合を再確認し、同名・同時刻の既存予定を重複作成しません。本人の明示的な反映操作と、外部カレンダーの逆同期は区別します。

## 保存、失敗、停止

`data/conversations.sqlite3`の`device_context_devices`に端末と取得状態、`device_calendar_events`に予定、`device_motion_intervals`に推定区間を保存します。端末・予定IDを一意キーにし、古い送信や再送は最新内容を上書きしません。成功した取得範囲だけを置換して削除・日時変更も追従します。範囲外の過去記録は90日まで保存し、次の正常な同期処理時に古いデータを削除します。

`POST /api/device-context/sync`は2MB、予定1,000件、移動3,000区間を上限とし、日付・型・範囲を検証してからトランザクションで保存します。件数超過や一時的な取得失敗を空の成功結果へ変換しません。`GET /api/life`は端末の同期状態・直近予定・時間の重なり・着手枠を返します。

iPhoneでは送信前に保護されたApplication Supportのファイルへ保存し、送信失敗時は次の機会に再試行します。権限失効・取得停止は送信待ちにも適用します。7日以上経過した未送信スナップショットは次の取得へ置き換えます。長期オフラインやOSの履歴上限を超えた空白を復元できるとは扱いません。

「暮らしのアシスタント」からカレンダー取得・移動取得・健康自動同期を個別に停止できます。カレンダー／移動の停止・権限拒否は次の成功した同期で、その端末の保存済み生データも削除します。すでに固定した会話根拠は別の記録として残ります。HealthKitの自動同期停止は既存の日次集計を削除しません。

BGAppRefreshの実行はiOSが決めます。アプリの強制終了中や長時間未起動時の即時取得・通知は保証せず、前景へ戻ったときにも取得します。常時録音、他アプリの閲覧履歴、メッセージ、写真や連絡先の一括収集は含めません。

## 健康集計の修正

HealthKitの読み取り拒否と記録なしをアプリから区別できないため、取得できない数値を0として同期しません。[Appleの権限仕様](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)。以前に認証操作を済ませたかは`getRequestStatusForAuthorization`で確認し、自動処理から再び許可画面を出しません。これは個々のデータへの許可の判定ではありません。

睡眠は当日正午を終端とする直近24時間のうち、その時点で読み取れた区間を集計します。`asleepUnspecified`・`asleepCore`・`asleepDeep`・`asleepREM`だけを対象にし、覚醒・inBedを除外、期間外を切り取り、複数端末や段階の重複区間を和集合にします。睡眠段階とinBedは重複し得ます。[Appleの睡眠データモデル](https://developer.apple.com/documentation/healthkit/hkcategoryvaluesleepanalysis)。健康集計の日付は端末のローカル日付です。

検証は`tests/test_device_context.py`、`tests/test_conversation_context.py`、`tests/test_life_native.py`の実JSON/Swift往復と睡眠区間計算、iPhone・MacのXcodeビルドを使用します。実機での権限付与とセンサーの観測は配布後の独立工程です。
