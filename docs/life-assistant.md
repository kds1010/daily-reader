# 暮らしのアシスタント

2026-09-07実装。iPhone・macOSの「今日」→「暮らしのアシスタント」から使用する。効果の数値は[生活改善の設計](conversation-value-design.md)の仮説であり、実測結果ではない。

## 利用の流れ

1. SoundcoreのMP3/TXTを共有し、録音ごとに「Codexでタスク・予定・関心などを整理」を開始する。抽出種別は既存5種類に`research`、`event`、`interest`、`preference`を追加した。既存のPlanner・コードAgentへのタスク切り出しは引き続き利用できる。
2. 候補の「調査・予定・関心・タスクにつなげる」で引用を確認する。保存済みの同種の項目はその詳細を開く。候補は自動実行せず、明示的に内容を確認して保存する。
3. 調査はタイトル・詳細・条件・期限・URLを確認して開始する。アプリを閉じてもMac miniのサーバーで続く。結果は結論、最大3選択肢、未確認事項、出典URL、最大5つの次の行動として保存する。結果からタスク・予定・追加調査を作れる。
4. 予定は開始・終了・タイムゾーン・申込期限・準備・出発・通知を個別に確認する。準備・申し込みを関連タスクへ切り出せる。予定の日時変更は、個別に上書きされていない未完了の関連タスクの期限・通知へ反映する。予定中止は関連する未完了タスクも中止する。元に戻しても中止タスクは自動復活させない。
5. カレンダーへの追加・変更・削除は予定詳細のボタンで実行する。Calendarの権限を要求し、Daymeldの項目IDマーカーがある予定だけを更新する。予定を保存しただけではカレンダーを操作せず、「申込済み」も実際の申し込み操作を代行しない。
6. プロフィールは対象者を必ず選ぶ。関心・目標・好み・本人が話した事実を区別し、修正、保管、見直し期限、完全削除に対応する。同名での自動統合や声による人物同定をしない。削除は保存したプロフィールと根拠コピーを消し、元録音は別途管理する。
7. 「今日」には期限順の対応中の予定・タスクを最大3件と、既存の地域制約を通ったハイライトから最大3記事を表示する。自分の有効な関心・目標のタイトルが記事に含まれる場合に優先する。第三者の好み、期限切れ、事実項目は推薦に使わない。既読・非表示記事は端末側で除外する。
8. 発言本文・確認した話者名・確認済み録音日・ファイル名を検索し、元の会話とGPS地図へ戻れる。検索は文字列一致、最大50件。地名の意味検索、GPSからの施設名推測、人物の自動同定は含まない。

## データと関連付け

同じ`data/conversations.sqlite3`に以下を保存する。Git管理対象外で、プロフィール一覧やGPSを調査プロンプトへ自動で含めない。

| テーブル | 内容 |
| --- | --- |
| `life_people` | 明示的に作成した人物ID・表示名。自分は固定ID `self` |
| `life_entries` | 種別、状態、検証済みJSON、元項目ごとの冪等キー、根拠スナップショット、作成・更新時刻、改訂番号 |
| `life_changes` | 作成・状態変更・予定変更の伝播の操作時刻。プロフィール本文を複製しない |
| `life_revisions` | 予定・タスクの修正前データと状態。プロフィールは対象外。詳細APIで直近20版を表示 |

関連は会話候補ID → 項目ID → 調査結果の行動番号 → 次の項目IDで保持する。会話根拠は引用と位置コンテキストを保存時点で固定し、再解析で上書きしない。録音IDから現在の会話・GPSにも戻れる。予定から作るタスクは役割`prepare`/`deadline`、調査は`research`を根拠に持つ。

保存の再送は同じ元ID・種別または手動の`request_id`を使い、1項目にする。SQLiteの書き込みトランザクションとUNIQUE制約で競合も防ぐ。編集は`revision`が一致する場合のみ受理する。日時はオフセット必須、UTC秒へ正規化し、予定の表示用タイムゾーンを別に保存する。日付だけの抽出を勝手に通知時刻へ変換しない。

HTTP API:

- `GET /api/life`: 項目、人物、最大3記事、通知予定。
- `GET /api/life/entries/{id}`: 根拠と変更前の記録を含む詳細。
- `GET /api/life/search?q=...`: 元会話の横断検索。
- `POST /api/life/entries`: 確認済みの項目作成。
- `POST /api/life/entries/{id}`: 内容・状態・調査の役立ち評価を改訂番号付きで変更。
- `POST /api/life/entries/{id}/delete`: プロフィールだけを改訂番号付きで削除。
- `POST /api/life/people`: 人物を追加。名前だけで統合しない。

## 調査の実行条件

`life_research.ResearchWorker`はWebサーバーと同じLaunchAgentで単一ジョブを順に処理する。コードAgentのキュー・リポジトリ操作から独立している。待機・実行中は計10件、1回最大600秒。キャンセル時はそのジョブのプロセスグループだけを終了する。サーバー再起動時の実行中ジョブは失敗として表示し、本人が再試行できる。保留中のジョブは継続する。APIキー環境変数は除外し、ChatGPTログイン状態を確認する。

Codexは一時ディレクトリから`--ephemeral --ignore-user-config --ignore-rules --sandbox read-only`、`web_search="live"`、シェルツール無効で呼び出す。構造化出力の件数・長さ・出典URLを再検証する。依頼内容の変更は再試行とは別に新規調査として確認する。個別調査のトークン消費には厳密な上限を設けておらず、アカウントのCodex利用枠を消費する。自動巡回・自動再試行・定期再調査はまだ行わない。

出典URLの存在だけで全内容が正しいと保証するものではない。利用時には確認時刻、未確認事項、出典を表示する。実行モードは[Codex公式設定リファレンス](https://developers.openai.com/codex/config-reference/)と導入済みCLIで確認した。

## 通知とカレンダーの境界

- 通知権限がある端末に、直近の将来の通知を最大40件予約する。40件を超えた分は次の更新で順に予約し、件数を画面で表示する。中止・完了・時刻変更で不要になったDaymeldの生活通知だけを削除・置換する。他のAgent通知は変更しない。
- 一度端末へ予約した時刻通知はOSが扱う。別端末での変更は、その端末が次にサーバーを取得した時点で反映する。通知の「予約」と本人が「気付いた」ことを混同しない。
- 調査完了・失敗通知は状態更新時に一度通知し、初回は過去分を通知しない。前景は30秒ごと、専用画面は15秒ごと、iPhoneの既存BGAppRefreshでも取得する。BGAppRefreshの実行時刻はOSが決めるため、アプリ終了中の即時通知は保証しない。APNsによる即時配信は未実装。
- カレンダーは[EventKit full access](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents(completion:))を明示操作時に要求する。端末内に項目ID→EventKit IDを保持し、再送は同じ予定を更新する。再インストールや別端末では予定開始の前後30日から同じURLマーカーを探す。マーカーを削除した予定や大幅に移動した予定の完全な重複検出は保証しない。外部での修正はDaymeldへ逆同期しない。変更・中止後は詳細画面の反映ボタンが必要。
- macOSはCalendar entitlementを追加し、HealthKit entitlementは含めない。Calendar/通知の実際の許可とiPhoneへのインストールはユーザーの端末操作工程となる。

## 評価と次の段階

調査結果に「役立った／使わなかった」、任意の本人見積もり節約分数を保存できる。未評価・未入力は0とみなさない。タスクの完了日時と予定の改訂履歴を保持する。ネット閲覧時間のOS計測や生活改善率の推定、集計ダッシュボードはまだ行わない。

次の段階は、許可した範囲の定期調査、イベント情報変更の検出、カレンダー双方向同期、人物・場所からの文脈検索、実測の比較画面である。現在の実装だけで自律的な予約、人物の自動同定、常時即時通知ができるとは扱わない。
