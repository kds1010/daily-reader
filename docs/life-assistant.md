# 暮らしのアシスタント

2026-09-07実装。iPhone・macOSの「今日」→「暮らしのアシスタント」から使用する。効果の数値は[生活改善の設計](conversation-value-design.md)の仮説であり、実測結果ではない。

## 利用の流れ

1. SoundcoreのMP3/TXTを共有すると、新規録音の文字起こし完了後にMac側でCodex整理を開始する。「一文で追加」へメモを書いても同じ処理に入る。既存のPlanner・コードAgentへの投入は本人が選ぶ。
2. 明確な約束はタスク、明示した調べものは調査、開始・終了が揃った参加予定は予定へ自動追加する。「いつか行きたい」、日時不明、推定の情報は「ここだけ確認」へ入力済みで表示し、不足だけ補う。不要な候補は取り下げられる。元会話・引用・GPSの根拠へ戻れる。
3. 調査はアプリを閉じてもMac miniで続く。自動調査は個人名・秘密情報を除いた公開質問文だけを使い、会話詳細・人物一覧・GPS・個人の期限は渡さない。自動開始は日本時間で1日3件、超過は翌日再開するか個別に確認して開始する。結論、最大3選択肢、未確認事項、出典、最大5つの次の行動を保存する。次の行動は確認候補とし、調査から連鎖的に追加調査を実行しない。
4. 予定の準備・申し込みを関連タスクへ自動で切り出す。予定変更は個別上書きのない関連タスクの期限・通知へ反映する。予定中止は未完了の関連タスクも中止し、申込済みなら申込タスクを完了する。中止タスクは予定を戻しても自動復活しない。
5. Calendarは初回のアクセス許可後、端末更新時に追加・変更・中止を自動反映する。Daymeldのマーカーがある予定だけを更新する。外部で編集・削除された予定は上書きせず、詳細からの再反映を求める。実際の申し込み・予約・購入は行わない。
6. プロフィールは録音内の対象者を一度選ぶと、その録音の同じ対象者の明示的な関心・好みへ選択を引き継ぐ。人物の訂正は個別に確認されていない引き継ぎ先も訂正する。別の録音の同名人物や声から人物を同定しない。修正・保管・見直し期限・完全削除に対応する。削除しても元録音と対象者の対応表は別途保持する。
7. 「今日」には期限順の対応中の予定・タスクを最大3件と、既存の地域制約を通ったハイライトから最大3記事を表示する。自分の有効な関心・目標のタイトルが記事に含まれる場合に優先する。第三者の好み、期限切れ、事実項目は推薦に使わない。既読・非表示記事は端末側で除外する。
8. 発言本文・確認した話者名・確認済み録音日・ファイル名を検索し、元の会話とGPS地図へ戻れる。検索は文字列一致、最大50件。地名の意味検索、GPSからの施設名推測、人物の自動同定は含まない。

## 自動化と確認の境界

2026-09-07のユーザー指示に基づき新規録音の自動処理を既定で有効にした。導入時刻をDBへ一度保存し、それ以前の録音や抽出済み候補をまとめて自動処理しない。既存録音は詳細から手動で開始できる。新規抽出は同時1件、失敗は間隔を空けて最大3回、6万文字超は手動開始へ戻す。アプリ上で自動整理全体または自動調査のみ停止できる。停止中の新規取り込みは再開後に処理し、開始済みの調査は個別に停止する。

絶対日時、または確認済み録音日時から解決できる相対日時だけを採用する。終了時刻は推測しない。日付だけのタスクはその地域の23:59を期限、9:00を通知にする。時刻指定タスクは期限時刻、予定は30分前、準備は前日を通知の初期値とする。これらは発言の事実ではなくアプリの編集可能な初期値であり、画面にも説明する。作成済みの自動項目はラベルと根拠の`confirmation=automatic`で区別する。

## データと関連付け

同じ`data/conversations.sqlite3`に以下を保存する。Git管理対象外で、プロフィール一覧やGPSを調査プロンプトへ自動で含めない。

| テーブル | 内容 |
| --- | --- |
| `life_people` | 明示的に作成した人物ID・表示名。自分は固定ID `self` |
| `life_entries` | 種別、状態、検証済みJSON、元項目ごとの冪等キー、根拠スナップショット、作成・更新時刻、改訂番号 |
| `life_changes` | 作成・状態変更・予定変更の伝播の操作時刻。プロフィール本文を複製しない |
| `life_automation_settings` | 導入時刻、自動整理・自動調査の停止設定 |
| `life_automation_recordings` | 自動抽出の試行回数と最終試行時刻 |
| `life_drafts` | 元録音と候補指紋などの一意キー、入力済み内容、確認理由、採否、作成先ID |
| `life_speaker_people` | 録音ID＋対象者ラベル→確認した人物ID。録音間の自動同定に使わない |
| `life_revisions` | 予定・タスクの修正前データと状態。プロフィールは対象外。詳細APIで直近20版を表示 |

関連は会話候補ID → 項目ID → 調査結果の行動番号 → 次の項目IDで保持する。会話根拠は引用と位置コンテキストを保存時点で固定し、再解析で上書きしない。録音IDから現在の会話・GPSにも戻れる。予定から作るタスクは役割`prepare`/`deadline`、調査は`research`を根拠に持つ。

保存の再送は同じ元ID・種別または手動の`request_id`を使い、1項目にする。SQLiteの書き込みトランザクションとUNIQUE制約で競合も防ぐ。編集は`revision`が一致する場合のみ受理する。日時はオフセット必須、UTC秒へ正規化し、予定の表示用タイムゾーンを別に保存する。日時の根拠が不明なら自動採用せず、原文と確認理由を残す。メモの再送はrequest_idで同一録音へ戻り、同じ文面を別の日に追加した場合は新しい録音と入力日時を保持する。

HTTP API:

- `GET /api/life`: 項目、人物、最大3記事、通知予定、自動化設定、確認候補。
- `POST /api/life/automation`: `enabled`・`research_enabled`を変更。
- `POST /api/life/capture`: 一文メモの`text`と冪等な`request_id`を保存。
- `POST /api/life/drafts/{id}/adopt`・`dismiss`: 入力済み候補の補足採用・取り下げ。
- `GET /api/life/entries/{id}`: 根拠と変更前の記録を含む詳細。
- `GET /api/life/search?q=...`: 元会話の横断検索。
- `POST /api/life/entries`: 確認済みの項目作成。
- `POST /api/life/entries/{id}`: 内容・状態・調査の役立ち評価を改訂番号付きで変更。
- `POST /api/life/entries/{id}/delete`: プロフィールだけを改訂番号付きで削除。
- `POST /api/life/people`: 人物を追加。名前だけで統合しない。

## 調査の実行条件

`life_research.ResearchWorker`はWebサーバーと同じLaunchAgentで単一ジョブを順に処理する。コードAgentのキュー・リポジトリ操作から独立している。待機・実行中は計10件、1回最大600秒。キャンセル時はそのジョブのプロセスグループだけを終了する。サーバー再起動時の実行中ジョブは失敗として表示し、本人が再試行できる。保留中のジョブは継続する。APIキー環境変数は除外し、ChatGPTログイン状態を確認する。

Codexは一時ディレクトリから`--ephemeral --ignore-user-config --ignore-rules --sandbox read-only`、`web_search="live"`、シェルツール無効で呼び出す。構造化出力の件数・長さ・出典URLを再検証する。依頼内容の変更は再試行とは別に新規調査として確認する。個別調査のトークン消費には厳密な上限を設けておらず、アカウントのCodex利用枠を消費する。調査そのものの自動再試行・定期巡回は行わない。録音の抽出再試行とは別の処理である。

出典URLの存在だけで全内容が正しいと保証するものではない。利用時には確認時刻、未確認事項、出典を表示する。実行モードは[Codex公式設定リファレンス](https://developers.openai.com/codex/config-reference/)と導入済みCLIで確認した。

## 通知とカレンダーの境界

- 通知権限がある端末に、直近の将来の通知を最大40件予約する。40件を超えた分は次の更新で順に予約し、件数を画面で表示する。中止・完了・時刻変更で不要になったDaymeldの生活通知だけを削除・置換する。他のAgent通知は変更しない。同じ予定から切り出した準備・申込タスクと同時刻の通知は1件にまとめ、準備完了・申込済みの段階通知は取り除く。
- 一度端末へ予約した時刻通知はOSが扱う。別端末での変更は、その端末が次にサーバーを取得した時点で反映する。通知の「予約」と本人が「気付いた」ことを混同しない。
- 調査完了・失敗通知は状態更新時に一度通知し、初回は過去分を通知しない。前景は30秒ごと、専用画面は15秒ごと、iPhoneの既存BGAppRefreshでも取得する。BGAppRefreshの実行時刻はOSが決めるため、アプリ終了中の即時通知は保証しない。APNsによる即時配信は未実装。
- カレンダーは[EventKit full access](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents(completion:))を明示操作時に要求する。端末内に項目ID→EventKit IDを保持し、再送は同じ予定を更新する。再インストールや別端末では予定開始の前後30日から同じURLマーカーを探す。マーカーを削除した予定や大幅に移動した予定の完全な重複検出は保証しない。外部での修正はDaymeldへ逆同期しない。初回許可後は前景/BGAppRefreshで自動反映する。端末内の同期版・内容署名と比較して外部編集を検出する。旧版の登録や別端末で見つけた既存予定は一度手動反映して連携を確立する。設定で自動反映を停止できる。Mac miniだけでは端末のEventKitを操作できない。
- macOSはCalendar entitlementを追加し、HealthKit entitlementは含めない。Calendar/通知の実際の許可とiPhoneへのインストールはユーザーの端末操作工程となる。

## 評価と次の段階

調査結果に「役立った／使わなかった」、任意の本人見積もり節約分数を保存できる。未評価・未入力は0とみなさない。タスクの完了日時と予定の改訂履歴を保持する。ネット閲覧時間のOS計測や生活改善率の推定、集計ダッシュボードはまだ行わない。

次の段階は、許可した範囲の定期調査、イベント情報変更の検出、カレンダー双方向同期、人物・場所からの文脈検索、実測の比較画面である。現在の実装だけで自律的な予約、人物の自動同定、常時即時通知ができるとは扱わない。

## iPhoneから追加する自動情報

既存カレンダー・移動区間・GPS速度・健康集計を自動取得し、予定の重なり、カレンダー上の着手枠、会話時の参考情報へつなぎます。取得失敗と情報なしを区別し、各取得を停止できます。詳しくは[自動取得コンテキスト](iphone-context.md)を参照してください。
